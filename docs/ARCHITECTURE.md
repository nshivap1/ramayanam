# Architecture

How Samskuru is put together and why. Decisions with their trade-offs are recorded in
[docs/adr](adr/0001-react-typescript-esbuild.md); this page is the map. What a game must do is in
[GAME_CONTRACT.md](GAME_CONTRACT.md).

## Goals and constraints

| Goal | Consequence in the code |
|---|---|
| Many independent contributors (people and agents) add games at the same time | A game is one folder; nothing central to edit; isolated checks per game ([ADR 0002](adr/0002-game-as-self-contained-folder-with-generated-registry.md)) |
| A learner can trust every akṣara | Sanskrit comes only from verified packs and deterministic engines ([ADR 0004](adr/0004-verified-content-packs-and-closed-world-sanskrit.md)) |
| Every game is testable without a browser, and daily puzzles are the same for everyone | Pure logic, seeded randomness ([ADR 0003](adr/0003-pure-logic-and-seeded-randomness.md)) |
| Forty games feel like one product | The shell owns top bar, help, results, XP, streak, share ([ADR 0005](adr/0005-shell-owned-session-chrome-and-result-flow.md)) |
| Works offline, on a cheap phone, with no account | Static PWA, local-first progress ([ADR 0006](adr/0006-local-first-progress-no-backend-in-v1.md)) |
| Few moving parts; installs and runs anywhere Node 22 runs | React + TypeScript + esbuild, `node:test` + Playwright, no other dependencies ([ADR 0001](adr/0001-react-typescript-esbuild.md), [ADR 0007](adr/0007-node-test-plus-playwright-no-test-framework-dependency.md)) |

Hard constraints: the runtime dependency list is `react` and `react-dom`; no network requests at
run time; no server; the built `dist/` must work from any URL path and from a file wrapper.

## Layers

```
 src/sanskrit ──▶ src/content ──▶ src/sdk ──▶ src/ui ──▶ src/games/<id> ──▶ src/app
   engine          verified         contract,   design      one folder          shell: routes,
   (translit,      packs            rng, quiz,  system,     per game            host, result,
   akṣara,                          progress,   QuizRunner                      profile
   sandhi, metre)                   storage
```

**Import rule: a layer may import only from layers to its left.** Aliases: `@sanskrit`, `@sdk`,
`@ui`, and one per content pack, `@content/<pack>` (`shabda`, `vocab`, `dhatu`, `sentences`,
`sandhi`, `samasa`, `subhashita`; shared types in `@content/types`). Details:

- `src/sdk` has no React at run time (only `import type`), no DOM and no `Math.random`, so game logic and progress run unchanged in Node, in a worker or behind a native wrapper.
- `src/content` may `import type` from `src/sdk` (packs tag items with the SDK's `Level`); that is the single type-only exception.
- Games import the package roots `@sdk`, `@ui`, `@sanskrit`, the packs they use as `@content/<pack>`, `react`, and their own files — never another game, never `src/app`.
- `src/app` is the only layer that knows the list of games, and it gets it from a generated file.

The rule is data in `tests/contract/platform.test.ts` (`MAY_IMPORT`) and every source file is
scanned against it on each run of the gate.

## Why a generated registry

`tools/gen-registry.mjs` scans `src/games/*` and `labs/*` for folders containing `manifest.ts` and
`Game.tsx` and produces two things:

- `src/app/registry.gen.ts` — `GAMES: GameEntry[]`, each entry a statically imported manifest plus a lazy `load: () => import('…/Game')`;
- `src/app/styles.gen.css` — the token and component sheets followed by each game's `style.css`.

Both are git-ignored and regenerated by every tool (`dev`, `build`, `test`, `typecheck`); on disk
they exist only for the type-checker and your editor. The bundler does not read them: an esbuild plugin (`registryPlugin` in
`tools/build.mjs`) feeds it the generated source directly, optionally restricted with
`--only=<id>`. That is what makes two properties possible at once: adding a game is "create a
folder", and a contributor can build and test *only their game* while a neighbour's folder is
broken. The catalogue, the learning path (`buildPath` in `src/app/screens/Learn.tsx`: games ×
`levels` × primary skill) and the daily list are all derived from manifests, so a new game appears
in the right places with no shell change.

## Game lifecycle

One session, from link to result:

1. **Route.** `#/play/<id>?mode=…&level=…&seed=…` is parsed by `parseHash` (`src/app/router.ts`). The router keeps the current route in memory as well as in `location.hash` (`currentRoute`, `navigate`, `useRoute`) and intercepts clicks on in-app `<a href="#/…">` links, so navigation still works in hosts that freeze or sanitise the hash (embedded frames, some webviews). `App` looks the id up in `GAMES`; an unknown id shows a not-found screen. A first-time visitor who is not deep-linking into a game sees the welcome screen first (`src/app/Onboarding.tsx`: starting level and script).
2. **Host.** `<GameHost>` (`src/app/GameHost.tsx`) resolves the mode (the query's if the manifest supports it, else `manifest.modes[0]`) and the level (`resolveLevel`: the nearest level the game has content for), then calls `entry.load()` — the game's code-split chunk is fetched here, not before.
3. **Seed.** Daily mode: `dailySeed(dateKey, id)`, the same for everyone that day. An explicit `?seed=` is used as given (plus the replay count). Otherwise a fresh seed per session.
4. **Context.** The host builds `ctx` (`GameContext`): seed, mode, level, settings, a namespaced `store`, and the callbacks `hud`, `finish`, `exit`, `sfx`, `haptic`, `announce`, `expose`. A new `ctx` — and so a remount of the game — is made for every session, seed, mode, level or script change.
5. **Play.** The game renders inside an error boundary. It reports progress with `ctx.hud(…)`; the host draws the top bar (close, progress, timer, score, hearts, help). On first launch the host shows the how-to-play sheet from the manifest.
6. **Finish.** The game calls `ctx.finish(result)` once (a second call is ignored with a console warning). The host calls `recordSession(profile, manifest, mode, result, dateKey)` — a pure function returning the new profile and what changed (XP, stars, streak, achievements).
7. **Persist.** The new profile goes to React state and to storage (`saveProfile`).
8. **Result.** The shared result screen shows stars, XP, streak, new achievements, the share card and the review list; "Play again" bumps the session counter (new seed, fresh game), a daily offers "Keep practising" in another mode.

With `?e2e=1` the host also publishes `ctx.expose` snapshots as `window.__game` and the recorded
result as `window.__result`, skips the automatic help sheet and does not register the service
worker; that is the whole test interface ([TESTING.md](TESTING.md)).

## State and persistence

All persistent state goes through a four-method key–value interface, `KV` in
`src/sdk/storage.ts` (`getItem`, `setItem`, `removeItem`, `keys`). `browserKV()` wraps
`localStorage` and degrades to memory when storage is blocked or full; `memoryKV()` is used in
tests. Keys:

| Key | Content | Written by |
|---|---|---|
| `samskuru:v1:profile` | The `Profile`: XP, streak (current, best, last day, freezes), XP per day (60 days), per-game stats, daily records (60 days), per-item mastery (Leitner box, due date), achievements, settings | shell, after every session and settings change |
| `samskuru:v1:game:<id>:<key>` | Whatever a game keeps through `ctx.store` (unlocked stages, an in-progress daily, "seen help") | that game only |
| `samskuru:v1:onboarded` | First-run welcome completed | shell |

`Profile` is a plain JSON object and every operation on it is a pure function in
`src/sdk/progress.ts` (`recordSession`, `effectiveStreak`, `dueItems`, `skillMastery` …).

**Versioning.** The `v1` in the key prefix is the storage schema generation; `Profile.version`
(`PROFILE_VERSION`) is the profile shape. `loadProfile` is a forward-compatible merge: missing
fields get defaults, wrong-typed fields are replaced by defaults, unknown fields are kept (so data
written by a newer build survives an older cached build). A breaking change adds a migration in
`loadProfile` and bumps `PROFILE_VERSION`. Game ids and mastery item ids are permanent because they
key saved data.

**The Safari eviction caveat.** Safari's tracking prevention deletes a site's script-writable
storage — `localStorage`, IndexedDB and service-worker caches included — after seven days of
browser use without the user interacting with that site
([WebKit, 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). A
learner who opens Samskuru in a Safari tab and returns ten days later can find their streak gone.
An app added to the Home Screen is not part of Safari and keeps its own usage counter, so its data
is not expected to be deleted. **Installing the PWA is therefore the supported way to keep
progress on iOS**, and the shell should say so. Not yet implemented: an install prompt,
`navigator.storage.persist()`, and export/import of progress as a file — see
[ROADMAP.md](ROADMAP.md).

**Future sync.** Because the profile is one serialisable value changed only through pure
functions, and storage is behind `KV`, an account backend is an additional `KV` (or a sync step
around `saveProfile`) rather than a rewrite. Merging two devices needs per-field rules (max of XP
per day, union of achievements, latest mastery record); those do not exist yet.

## Build pipeline

`tools/build.mjs` (run by `npm run build`, and by the gate after `npm run validate` has checked the content packs):

1. Generate the registry.
2. Bundle `src/app/main.tsx` with esbuild: ESM, `splitting: true`, target ES2020, minified, content-hashed names. Each game's `Game.tsx` becomes its own lazy chunk; code shared by several chunks is split out automatically.
3. Copy `public/` (fonts, icons, web manifest) and write `index.html` from the template, filling `<!--CSS-->` and `<!--JS-->`.
4. Write `sw.js` from `public/sw.js`, filling `__VERSION__` (a hash of the output) and `"__PRECACHE__"` (every built file).

Every URL in the output is relative (`./assets/…`), and navigation uses the URL hash
(`#/play/<id>`), so `dist/` can be served from a domain root, a sub-path, a preview URL or a
native wrapper's file scheme without configuration or server rewrites.

`tools/dev.mjs` runs the same bundle unminified with esbuild's watch mode and a static server;
`tools/serve.mjs` is the zero-dependency static server used by dev, preview, screenshots and
browser tests. `tools/build.mjs --only=<id> --outdir=<dir> --no-sw` builds a single game into a
private folder (used by `--game=<id>` checks and by `tools/screenshot.mjs --game=<id>`).

## PWA and service worker

- `public/manifest.webmanifest`: standalone display, relative `start_url` and `scope`, 192/512 px icons plus a maskable icon.
- `public/sw.js` (template): on **install**, precache every built file and activate immediately; on **activate**, delete caches of older versions and take control of open pages; on **fetch**, navigations are network-first with the cached shell as offline fallback, everything else (content-hashed assets, fonts, icons) is cache-first.
- The app is fully playable offline after the first load; the shell browser test proves it (`tests/e2e/shell.spec.ts`).
- The service worker is registered only in production builds and never when the URL contains `e2e=1`.
- A new deployment gets a new cache name; the next navigation while online picks up the new shell.

## Performance budget

Measured on the reference build (platform + the two reference games); the first three rows are
enforced by `tests/contract/platform.test.ts`.

| Asset | Budget (minified) | Now | Notes |
|---|---|---|---|
| Entry JS (`app-*.js`: React, shell, SDK, UI kit) | ≤ 300 kB | 218 kB (67 kB gzip) | Loaded before first paint. React is most of it. |
| CSS (`app-*.css`: tokens, components, shell, all game styles) | ≤ 60 kB | 31 kB (7 kB gzip) | One sheet; games add a few hundred bytes each. |
| A game's own chunk (`chunks/Game-*.js`) | ≤ 30 kB | 4–6 kB (≈ 2 kB gzip) | Loaded when the game opens. |
| Shared chunks (Sanskrit engine, quiz runner, content used by several games) | watch | 103 kB (25 kB gzip) | Loaded with the first game that needs them. Content packs will dominate here — see *Scaling*. |
| Fonts (2 TTF files) | ≤ 1.5 MB | 1.4 MB | Cached by the service worker after first load. Converting to subsetted WOFF2 would cut this by more than half; not done yet. |

Rules that keep it there: no runtime dependencies beyond React; a game never blocks the main
thread for more than 50 ms; images and audio are not bundled today (see [ROADMAP.md](ROADMAP.md)).

## Accessibility commitments

- **Touch:** interactive targets are at least 44 × 44 px; layouts work at 360 × 640 with no horizontal scroll (checked in browser tests with `expectNoOverflow`).
- **Keyboard:** every action is reachable without a pointer; `<QuizRunner>` supports digits and Enter; a visible focus ring comes from the design system.
- **Screen readers:** Sanskrit text carries `lang="sa-Deva"` or `lang="sa-Latn"`; sheets are modal dialogs that close on Escape; progress is a `progressbar`; games announce visual-only events through `ctx.announce` (a polite live region).
- **Motion:** a Reduce motion setting and the OS preference both collapse animations; JS and canvas loops must check `ctx.settings.reducedMotion`.
- **Colour:** light and dark themes from the same tokens; feedback pairs colour with a ✓ / ✕ mark and text. Not yet done: a high-contrast palette, a text-size control and colour-blind-safe tile shapes ([ROADMAP.md](ROADMAP.md)).
- **Script:** every Sanskrit string can be shown in Devanagari or IAST, chosen once in settings.

Automated tests cover overflow, console errors and keyboard paths a game's own spec exercises;
screen-reader behaviour is checked by hand ([TESTING.md](TESTING.md#what-is-not-tested-automatically)).

## Path to a standalone app

`dist/` is a self-contained static site with relative URLs and hash routing, so wrapping it with
[Capacitor](https://capacitorjs.com/) needs no change to games. What would change, all behind
existing seams:

| Concern | Today | In a native wrapper |
|---|---|---|
| Storage | `browserKV()` over `localStorage` | A `KV` backed by native key–value storage. `KV` is synchronous, so the wrapper loads all `samskuru:` keys into memory at start and writes through. This also removes the Safari eviction problem. |
| Haptics | `navigator.vibrate` in `src/app/audio.ts` (no effect on iOS) | The native haptics plugin behind the same `vibrate(kind)` function |
| Share | Web Share API or clipboard in `src/sdk/share.ts` | The native share sheet behind `share(text)` |
| Splash and icons | Web manifest icons | Native icon and splash assets generated from `public/icons/icon.svg` |
| Deep links | `#/play/<id>?mode=daily` | App links mapped to the same hash routes |
| Offline | Service worker | Assets ship inside the app; build with `--no-sw` |
| Updates | New deployment, new cache | Store release, or a live-update channel for `dist/` |

What a **backend** would add later (none of it exists; each needs its own ADR):

- **Accounts and sync** — the same profile on several devices; recovery after a lost phone.
- **Leaderboards and leagues** — weekly cohorts, class-code boards for a teacher's batch.
- **Friend and class quests** — shared streaks and cooperative weekly goals.
- **Live class mode** — a teacher hosts a quiz or a Tambola caller; students join with a code.
- **Content delivery** — new packs and daily puzzles without an app release, with the same verification gates applied server-side.
- **Push reminders** — which on iOS also require an installed PWA.

## Scaling to 100+ games

- **Code:** each game is a lazy chunk, so the entry bundle does not grow with the number of games — only by one manifest (a few hundred bytes) each.
- **Catalogue and path:** driven by manifests (kind, skills, levels, modes); filters and the per-level path need no per-game code. At 100+ games the Games screen will need search and grouping.
- **Service worker:** it currently precaches every chunk at install. That is right for 10–40 small games. Beyond that, precache the shell and fonts only and cache game chunks on first play (the fetch handler already caches on demand).
- **Content packs:** a pack is ordinary code, imported one pack at a time (`@content/<pack>`), so the bundler puts each pack only into the chunks of the games that use it. Large packs (a full lexicon, verse banks) should become lazily loaded JSON with a small typed loader, so a script-learning game does not download verb paradigms. This is a future step and will need an addition to the contract (`ctx` handing loaded content to the game).
- **Styles:** all game CSS is concatenated into one sheet; scoping under `.g-<id>` keeps it conflict-free. If it grows past the budget, per-game CSS can move into the game chunks.
- **Quality:** `labs/` is the channel for experiments, `beta` for reviewed-by-machine games, `stable` for human-reviewed ones ([CONTRIBUTING.md](../CONTRIBUTING.md#labs-beta-stable)). The contract tests run per game, so gate time grows linearly and each contributor pays only for their own game.
- **Type-checking:** one `tsc` run over the repo is the slowest step of the full gate; project references per layer are the known remedy when it hurts.
